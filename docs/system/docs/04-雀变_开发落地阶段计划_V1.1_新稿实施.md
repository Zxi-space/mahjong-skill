## 01. 先明确阶段管理原则

1. **唯一核心目标**：将真实线下麻将需要购买/打印的技能牌，转为可以抽取、持有、发动、记录的电子卡牌；**不开发线上麻将对局、实体麻将手牌/牌河/牌墙、自动摸牌/出牌/碰杠胡/番型计分**。
2. **保留优先级**：原规则 P0 必做；预设效果模板在 P0 需具备后端合法性与参数校验，但**面向普通用户的自定义创作器仍是 P1**；P2 社区/付费等功能不进入首发。
3. **三端共用数据与规范**：用户端 (Mini/H5) 是主要业务入口；Admin 提供官方内容与排查所需的最小管理面；Portal 负责品牌展示和进入产品。2026-10-30 三张新批准的浅色稿确定布局，美术不重新发散；Dark 是对位适配。
4. **每阶段只交付可验收增量**：任务清单、增量源码/测试/迁移、实际运行证据、中文 Git Commit 建议；阶段报告不塞进代码增量包，阶段信息可直接在对话/独立规划文档中汇报。
5. **先业务一致性，后效果包装**：禁止以一张静态截图、假按钮或纯页面跳转冒充功能实现；任何页面既有空/错/加载/成功状态，也有真实 API/操作路径。
6. **版本冻结**：正在进行的局/房间沿用开局时的卡牌与规则快照；更新官方卡牌不得污染正在进行的局。
7. **阶段编号只用于计划**：正式代码模块、路由、组件不写 `phase1` / `g0` 等临时阶段名称。

### 1.1 验收门（Gate）

每阶段合格必须同时满足：①阶段功能真实可用；②依赖与错误处理正确；③关键自动化测试通过；④ Light/Dark 视觉不回归；⑤ 数据迁移可重复；⑥ 不违反玩法安全边界；⑦ 提交变更影响与下一阶段依赖清楚。**未过门不进入强依赖的下阶段**；设计/素材任务可在不影响规则的前提下并行。

## Phase 01｜基线冻结与技术方案

**2026-10-30 新增视觉与边界核验**：三张 `../references/01-client-approved-20261030.webp`、`../references/02-portal-approved-20261030.webp`、`../references/03-admin-approved-20261030.webp` 为新视觉唯一基准；旧浅色稿不再验收。恢复**雀叽家族麻将牌七角色**，拒绝鸡/鸟；产品只处理电子技能卡，房间没有实体麻将手牌/线上打麻将。



**前置**：以现有三份来源规范为唯一版本；不得重新商议已确认玩法。  
**任务**：
- 建立 `P0/P1/P2` 需求追踪矩阵，标识“已通过规则”“已通过视觉”“需定义实施细节”“待试玩验证”；统一 24 张原创牌的 ID、5 类、15 个模板代码，不用视觉占位卡名覆盖规则。
- Mini/H5 共用技术路线已经确定为 **React + TypeScript + Taro**；使用微信开发者工具和 H5 浏览器完成二维码/分享/可选登录/主题/安全区/路由 PoC。如发现平台兼容问题，先形成 ADR 与修复方案，不擅自更换技术选型。
- 后端候选：FastAPI + PostgreSQL + 事务化状态存储 + WebSocket；Redis 可按多实例广播、临时会话/限流实际需要引入，不以 Redis 作为唯一业务状态真相。
- 明确 4 人匿名会话、房间身份、四位成员/东南西北座位标识（仅真实线下座位标签）、抽卡隐私、回合与局、技能动作及争议的领域模型；明确小程序发布与 H5 分享行为的端差异。
- 整理“插画与真实功能”边界：页面中的实体麻将牌墙/摸牌/胡牌按钮即使为氛围素材也不得设计成可交互麻将牌桌/手牌；VIP/支付/购买不进入 P0；不作在线麻将模拟器。
- 审核项目基础域名/环境配置方式、开发/测试/生产分离方案和最小管理员权限模型。

**交付**：架构决策记录（ADR）、需求追踪矩阵、核心数据字典/API 草案、Mini/H5 PoC、设计稿误导项清单。  
**Gate 01**：可以清晰回答“谁能看到私有卡”“哪个状态允许发动”“谁决定随机结果”“断线如何恢复”；至少演示 Mini 与 H5 关键 API/页面能力，业务范围没有新增未批准功能。

## Phase 05｜经典卡盒：单设备可玩闭环

**视觉 Gate**：以新用户端参考的卡库/详情/抽牌体验为基线；该模式是在真实麻将旁边通过一台手机传递电子技能卡，不渲染实体麻将手牌/桌面，也不提供电子“摸麻将牌”或“出麻将牌”行为。



**依赖**：Gate 03 + Gate 04。  
**任务**：
- 2–4 人模式选择、选牌库、按人数检查库存、洗牌分配、默认每人 2 张，单局无副本时不重复发相同卡实例。
- 设计与实现“按住查看私有技能卡—松开遮盖—递给下一人”流程；清晰提示单设备隐私限制。
- 支持卡详情、手动已使用/放弃/弃牌、规则提示、误触有限撤销、下一局重新洗牌和本机状态恢复。
- 保留原有“自由工具优先，标准限制可开启”的待试玩默认项；无网络房间/强制注册依赖；可用本机数据继续处理已缓存操作。
- 记录每局基本事件用于排查；清晰区分“现实麻将一局”和“手机操作流程”。

**交付**：可在一台真实手机连续使用的经典卡盒 P0。  
**Gate 05**：完全无账号从首页进入→选择牌库→顺次抽牌→按住查看→使用/弃置→下一局全过程成功；牌数、使用次数、掩盖、刷新恢复和不可逆操作均有测试；不以“完整离线 PWA”作为 P0 承诺。

## Phase 06｜四人好友牌桌与实时同步

**关键页面纠偏**：用户端房间是**电子技能房间**，UI 只包含房号、二维码/邀请、四人在线/就绪、当前局标记、本人的电子技能卡及公开技能事件。东南西北只可作为座位文本；**不得出现模拟麻将桌、实体麻将手牌或“出牌/摸牌/碰/杠/胡”的控制按钮**。



**依赖**：Gate 04，Phase 05 共享 UI 可复用。  
**任务**：
- 四人房间创建，房主选牌库、模式规则/进阶开关；二维码与短房间码入房，匿名会话令牌与有效期；四个位置固定东南西北。
- 完整状态流：`WAITING → READY → DEALING → PLAYING → SETTLING → PLAYING（下一局）/ CLOSED`；成员就绪，全员确认规则后才能开局。
- 后端控制联网洗牌/随机种子/私有技能卡分发；私有技能严格单人可见，公开事件按授权广播。
- WebSocket 事件结构含 `room_id / hand_id / event_seq / action_id`；断线后快照与增量事件能对账，房主退出有可解释处理路径。
- 禁止旁观者进入私有抽卡链；房间满员、重复加入、令牌过期有可用反馈。

**交付**：四台设备可真正完成建房、入房、就绪、开始、领私有技能卡和局末。  
**Gate 06**：四台真机/模拟设备分别接收自己私有技能卡；用 API、WS 抓包验证绝不下发他人私有技能卡；多端状态一致、每局随机结果服务端确定，刷新后可恢复。

## Phase 07｜技能效果、响应和结算状态机

**交互语义**：按钮为“使用技能”“选择受影响玩家”“防御/放弃响应”“现场已执行”“申请处理争议”，均操作**电子技能事件**。如模板关联实体麻将操作，只能提示桌边玩家协商执行、人工确认，禁止手机判定合法性。



**依赖**：Gate 06。  
**任务**：
- 实现七状态：`AVAILABLE / PENDING_RESPONSE / PENDING_MANUAL / RESOLVED / COUNTERED / VOIDED / DISPUTED`，且每一步只可由有效动作转换。
- 发动检查：卡版本/归属、房间与局状态、`BEFORE_HAND / OWN_TURN_BEFORE_DISCARD / ON_TARGETED / ON_DECLARED_EVENT / AFTER_HAND` 时机、目标、主动/防御次数、库存与模式。
- 一次只处理一条技能；目标玩家防御或放弃、至多一层响应；不得锁屏超时自动放弃。
- 实现“系统能处理”的抽电子牌/交换电子技能/公开状态/娱乐星，与“必须在现场执行”的查看暗牌/换实体牌等明确隔离；后者要求当事玩家确认。
- 实现被动技能由玩家声称事件触发，系统不检查真实碰、杠、胡；娱乐星不绑定番数或资金。
- 同一动作强制 `action_id` 幂等，结算数据事务性一致；同一张卡不能重复消耗或重复给星。

**交付**：15 模板相应效果处理器的受约束 P0 运行能力，联机技能完整处理链。  
**Gate 07**：五类技能代表案例全通；非法发动不扣次数，成功/防御/作废/争议均有正确日志；任意时刻仅一项技能结算，不能越权调用模板或无限反弹。

## Phase 08｜弱网、异常和隐私的生产级强化

**隐私视觉**：技能卡背是私有电子技能的遮罩，不是线下麻将的暗牌；未公开的卡不下发到其他玩家设备，断网恢复不展示他人卡面。



**依赖**：Gate 07。  
**任务**：
- 断线重连：按快照 + 事件序号补齐，不能重播导致重新抽卡/重复记星；中断技能保持待确认，不被静默完成。
- 房主失联/玩家离席/取消技能/无法线下执行的争议流程：基于玩家线下共识允许人工裁定；已泄露电子/实体隐私的不可逆结果不能“回滚为未发生”。
- 最少权限：房主、玩家、管理员；匿名令牌轮换与过期、敏感日志脱敏、前端错误提示不泄露其他人牌面信息。
- 压测重复点击、并发发动、掉线重入、刷新/重进房、不同端日期/时间错乱；校验数据库事务和实际网络恢复。
- 加入运行监控与电子事件审计；异常状态提供安全终止手段，不允许永久卡死。

**交付**：可靠房间与动作处理、可追踪日志、异常处理策略、自动化并发测试。  
**Gate 08**：隐私泄露、重复结算、掉线丢失不可逆状态、争议永久卡死均为一票否决；所有模拟异常能够正确显示状态、恢复或安全终止。

## 03. 核心数据模型与接口分区（建议，不强制特定 ORM）

| 领域 | 建议核心数据 | 关键约束 |
|---|---|---|
| 官方内容 | `SkillDefinition`, `SkillVersion`, `EffectTemplate`, `Deck`, `DeckVersion` | 稳定 ID、公开版本、进阶标记、模板参数白名单 |
| 单机局 | `LocalSession`, `LocalHand`, `LocalSkillInstance` | 手机本机可恢复、不依赖在线账号 |

**接口建议**：按 `/api/v1/skills`、`/decks`、`/rooms`、`/hands`、`/actions`、`/admin/...` 领域组织；`WS /rooms/{id}/events` 用于通知，不允许仅凭前端 WS 事件改变服务端状态。实际路径由 Phase 01 技术设计定稿，**不能把此表误认成已经批准 API 合同**。

## 07. 一票否决与变更控制

**一票否决**：未经现场全员同意自动改变实体麻将、泄露他人私有技能、客户端决定随机结果或重复结算、无争议/撤销路径而永久卡死、娱乐星与真钱联动。出现任何一项立即中止该阶段验收。

**变更记录模板**：`CR 编号 | 来源 | 原定义 | 新定义 | 受影响 P0/P1/P2 | 对应页面/组件/卡片/Schema | 是否经过确认 | 迁移/回滚策略`。未确认 CR 不能改变已批准功能。

> 完成定义：只有 Phase 11 Gate 通过才可以称 P0 正式上线；Phase 12/13 不应被自动标记为已经完成或作为首版发布前置条件。
