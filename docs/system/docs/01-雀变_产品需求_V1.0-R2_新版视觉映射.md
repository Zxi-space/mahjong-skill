## 00A. 新版视觉基线与 UI 语义（2026-10-30 批准）

- **三张新的视觉基线**分别是 `references/01-client-approved-20261030.webp`、`02-portal-approved-20261030.webp`、`03-admin-approved-20261030.webp`；**旧版三端效果图均降级为历史参考**。
- 新样式为**米白底、深麻将绿、柔和植物绿、暖橙点缀、简约线描/轻扁平插画、清晰功能组件**。禁止恢复之前的水彩麻将馆全景、塑料金边卡框、鸟类/小鸡拟人 IP。
- 正式 IP 是**拟人化麻将牌“雀叽家族”七位成员**：红中、发财、白板、东、南、西、北。角色**必须保持麻将牌轮廓与牌面文字/空白特征**；不得有喙、翅膀、羽毛和小鸡身体。
- **小程序/H5 技能房间**仅显示房号/好友在线及就绪/电子技能卡/发动与响应/规则与事件记录。**不得呈现实物麻将手牌、线上牌桌、牌墙、牌河、摸牌、出牌、碰杠胡等交互**。
- 为避免歧义，**UI 文案统一使用“我的技能卡 / 我持有的技能卡”**；原玩法文档中的“私有手牌”特指电子技能卡，**不修改原文与业务含义**。
- 新设计稿里展示的卡名、数值、统计和按钮是**示意内容**；24 张官方牌及 15 预设模板以已通过的玩法规则为准，统计值需接入真实 API。会员/付费/商品/线上麻将操作不是 P0 需求。
- Light 作为当前已审定的视觉母版，Dark“夜局模式”继续保留为已确认的设计需求；以**新 Light 页同结构**进行夜色适配，不能沿用老版夜间麻将室布局。

## 00. 结论：做什么，不做什么

**一句话定位**：雀变是线下实体麻将的**电子技能卡牌工具**。玩家继续面对面打真实麻将，系统负责电子技能牌的抽取、持有、发动、结算状态、同步与记录；系统不替代实体麻将的操作或规则裁判。

**明确包含**：官方技能牌和牌库、经典卡盒单机模式、好友牌桌四人联网模式、技能状态机、模板化自定义卡牌及自定义牌库、分享、必要的运营管理与产品介绍页面。后三者在 V1 规则中的优先级分别为 P1/P1/三端后续补充，不可擅自升为首发 P0。

**明确不包含（V1）**：线上麻将棋盘、真实摸牌/碰杠胡模拟、麻将图像识别、自动胡牌判定、番型及输赢计分、真钱下注与结算、付费抽卡、卡牌养成、任意代码/脚本技能、无限技能连锁。娱乐星仅用于现场趣味展示，绝不关联资金或麻将番数。

### 03.1 经典卡盒操作链路

`选牌库 → 设定人数与模式 → 本机洗牌 → 按玩家轮流抽 2 张 → 按住私密查看 → 线下打麻将 → 亮牌/使用/弃牌 → 下一局重新洗牌`

模式特征：**工具优先**，本机卡牌标记由玩家操作，不强制其他人在手机上确认；自由使用方式可以不启用标准局次数严格限制。

### 03.2 好友牌桌操作链路

`房主创建房间 → 成员扫码/码入房 → 全体查看牌库和规则 → 就绪 → 房主开局 → 服务端发私牌 → 发起/响应技能 → 电子或实体结算确认 → 局末 → 下一局或结束房间`

网络房间要保证**一项技能结算结束前不开始另一项**，服务端负责权限、状态与顺序一致性。

### 03.3 原规则已经定义的标准局参数

| 参数 | 默认值/边界 |
|---|---|
| 参与人数 | 好友牌桌固定 **4 人**；经典卡盒推荐 **2–4 人** |
| 初始电子技能卡数量 | 每人 **2 张** |
| 个人技能卡持有上限 | **3 张**，超限时必须弃置多余电子技能 |
| 主动技能 | 每人每局最多 **1 张**（标准局） |
| 防御响应 | 每人每局最多 **1 张**，不占主动次数 |
| 被动卡 | 每张每局最多触发 **1 次**，相关玩家现场确认 |
| 单张卡消耗 | 结算后移入使用/弃牌，不回到当前局手牌 |
| 跨局继承 | **默认不继承** |
| 进阶实体操作 | **默认禁用**；启用需全员知情同意且不与地方规则冲突 |
| 自动麻将规则判定 | **不支持** |

## 09. 全链路业务验收要点

| 测试项 | 合格标准 |
|---|---|
| 经典卡盒从零开始 | 无账号一机可完成选库→按玩家抽两张→隐藏→使用/弃置→下一局 |
| 4 人组局 | 建房→扫码/码入→规则确认→全员就绪→开始→发牌成功 |
| 个人私有技能卡 | 其他玩家的会话从网络接口和 UI 都无法读取未公开卡牌 |
| 发动时机 | 非法时机/次数用完/目标非法明确拒绝，并不多次消耗 |
| 防御链 | 最多一层，不发生无限反弹；默认不自动超时放弃 |
| 实体技能 | 提示现场执行并保留确认/争议入口，不臆造真实麻将合法结论 |
| 并发操作 | 多人同时点技能只允许一次生效，`action_id` 去重 |
| 断网重连 | 恢复到服务端快照；争议/待人工确认状态保持可继续处理 |
| 规则版本 | 已开始的房间沿用开局冻结版本；编辑官方卡不影响进行中局 |
| 手绘 + Dark | 两套主题按钮、文字、表格、卡牌都可读，主题切换不清空状态 |
| 官方卡牌 | 24 张候选概念牌可展示，进阶 A02/A03/A04 默认禁止 |
| 阶段控制 | P0 全部完成后再进入 P1，P2 不在 V1 首发验收内 |

### 一票否决项（原版保持）

- 未得到桌上玩家同意就自动改变实体麻将操作。
- 泄漏其他玩家的私有电子技能。
- 让客户端篡改随机结果或重复提交多次结算。
- 没有撤销或争议出口导致牌局永久卡死。
- 把娱乐星或卡牌奖励自动绑定真实赌资。

## 10. 已知待验证项与变更控制

| 项目 | 状态 | 处理方式 |
|---|---|---|
| 24 张基础技能的平衡性 | 待 3–5 桌线下试玩验证 | 不当作已验证的最终技能数值 |
| 单机自由工具 vs 严格次数校验默认项 | 原规则倾向自由工具优先 | 实测后再确认默认配置，不改变模式定义 |
| 娱乐星默认开关 | 可选，绝不与真实输赢挂钩 | 通过线下试玩决定默认开关 |
| 进阶实体牌可用性 | 原规则明确默认关闭 | 必须考虑地方规则冲突 |
| 后台权限矩阵和审核时序 | 三端设计系统页面已有，业务规则待细化 | 不反向覆盖原始 V1 玩法基线 |
| 会员/VIP/消费入口 | **非已确认功能** | 视觉稿占位不得进入首发需求 |
| 完整线上麻将 | **明确不做** | 场景插画不能变成麻将模拟器研发任务 |

若后续提出更改某一确定需求，应单独记录：**变更编号 → 原需求 → 新需求 → 影响的功能/页面/后端 → 是否经确认**。不在整理文档时偷偷改变既有范围或优先级。
